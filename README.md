# 告警关联运行系统（alertcorr）

首个功能：把同一故障引起的重复告警归并为一个事件，并处理恢复与再次发生。

## 设计要点

- **合并依据身份而非相似度**：只有 fingerprint（source+check）与轮次（epoch）都相同的
  firing 告警才并入已有事件；绝不按消息文本相似度合并。
- **恢复与再次发生**：恢复告警必须携带与活动事件相同的 epoch 才能关闭它；
  迟到恢复（旧 epoch）记为 stale_recovery，不会关闭新一轮事件；新一轮 firing 开新事件。
- **父故障抑制子告警需显式依赖证据**：子告警必须自带 depends_on 声明，且规则集的
  依赖图确认该边，才被活动父事件抑制；抑制关系持久化在 suppressions.json，重启后仍生效。
- **依赖图变更影响审查**：ReviewRules 应用新规则集时逐条核对父事件仍活动的抑制，
  被撤销的边对应抑制解除、子告警重新立为活动事件；原抑制记录与其判断所用规则版本
  永久保留，审查过程写入 reviews.json 审计。
- **父告警迟到**：父事件开火时，此前因父未活动而独立成事件、且带依赖证据的子事件
  改判为抑制。
- **分析人员解除/重判**：LiftSuppression 暂时解除一条抑制并返回证据（原告警、父事件、
  原判断规则版本、当前边是否仍确认）；RejudgeSuppression 操作结束后按当前状态重判，
  边仍确认且父事件仍活动则恢复抑制，否则正式解除。
- **重复重放无副作用**：同一告警 ID 重复提交返回 replayed，不重复落库；
  通知按 kind+事件+详情去重，重放不产生多份通知。
- **分离持久化**（data 目录下）：
  - rules.json —— 规则集及版本（每个事件记录处理它的规则版本）
  - alerts.json —— 原始告警，逐条原样保存
  - incidents.json —— 事件身份（含开始/结束、合并与抑制的告警来源）
  - suppressions.json —— 抑制关系
  - reviews.json —— 依赖图变更影响审查审计
  - notifications.json —— 通知仅写入本地记录（FileRecording），不外发
- **通知暂不外发**：notify.Notifier 接口已定义，Recording/FileRecording 只记录事件，
  后续可直接接通知通道。

## 运行内置“依赖服务故障序列”

```sh
go run ./cmd/alertcorr -data /tmp/alertcorr-data
```

序列覆盖：父故障开火 → 重复告警合并 → 子告警按依赖证据抑制 → 恢复 →
再次发生（新 epoch 新事件）→ 迟到恢复不得关闭新事件 → 模拟重启后抑制关系仍生效 →
第二轮恢复关闭事件 → 父告警迟到改判子事件 → 分析人员解除/重判抑制 →
规则撤回的影响审查 → 重启后新子告警按新规则抑制 → 重复重放不产生多份通知。
结束后逐条核对每个事件的开始、结束与被合并来源并输出报告；
任何一项失败则以非零码退出。通知只写本地记录不真实发送。
